# 联机设计（M6 基础框架）

> 状态：M6.0 传输层 + 快照序列化已完成；房间、单位同步、重连等在上层集成后逐项落地。
> 代码：`scripts/net/protocol.gd`、`scripts/net/snapshot.gd`、`scripts/net/net_session.gd`；测试：`tests/net_test.gd`。
> 边界：本阶段不修改 `scripts/core/main.gd`、`scripts/ui/*`、`scripts/units/*`、`scripts/world/*`，由 Lead 负责把网络层接进主循环。

## 1. 目标与非目标

### 目标

- **服务端权威**：单位物理、玩家代码执行、伤害/资源结算全部在服务端；客户端只发“意图”和“代码”，只收“结果”。
- **固定 20Hz tick**：服务端以 50ms 为一步推进模拟，快照按 tick 广播；客户端用插值平滑显示。
- **代码即玩法**：玩家为单位编写类 Python 代码，源码上传到服务端，在已有沙箱 VM 中执行；客户端不执行权威逻辑。
- **可预估的带宽**：二进制定长编码，2 队 × 20 单位时单客户端下行约 150 kbit/s。
- **可测试**：协议、快照、UDP 会话都能在 headless 下用纯 GDScript 测试，不依赖场景树。

### 非目标（M6.0 不做）

- 不做客户端预测/回滚（单位由服务端模拟，客户端只插值）。
- 不做确定性 lockstep，不使用 Jolt 做跨端确定性物理。
- 不做 NAT 穿透、加密、账号系统、匹配大厅；这些放在 M6.1 之后。
- 不做 UDP 分片/可靠重传；M6.0 的单包快照控制在 MTU 以内（当前 2×20 单位 = 933B）。

## 2. 网络模型

### 2.1 权威拓扑

```
玩家 A 客户端 ──┐                      ┌── 单位 VM / 物理 / 资源结算
                ├── UDP ── 服务端进程 ──┤   （固定 20Hz tick）
玩家 B 客户端 ──┘                      └── 快照广播（每 tick）
```

- 只有一个权威服务端；客户端不互连（不做 P2P）。
- 客户端发送：`HELLO`、`CODE`、`INPUT`、`PING`。
- 服务端发送：`WELCOME`、`SNAPSHOT`、`PONG`、`ERROR`。
- 单位代码在服务端沙箱 VM 中运行，产出 `set_lift/set_tilt/set_rcs/drill` 等控制量；这些控制量**不经过网络**，直接在服务端进入物理。

### 2.2 服务端 tick 循环

每个 tick（50ms）：

1. 处理本 tick 收到的 `INPUT` / `CODE` / `HELLO`（先入队，避免在收包回调里做重活）。
2. 对每个单位：注入传感器读数 → 跑 VM（行预算 + 指令预算）→ 得到控制量。
3. 物理步进（服务端唯一物理权威）。
4. `Snapshot.capture(units, tick)` 生成快照。
5. `broadcast(MSG_SNAPSHOT, snapshot)`。
6. `tick += 1`。

建议用“累加器 + 最多追 2 步”的方式驱动，避免服务端卡顿后一次性补太多 tick：

```gdscript
_accum += delta
var steps := 0
while _accum >= TICK_DT and steps < 2:
    _simulate_one_tick()
    _accum -= TICK_DT
    steps += 1
if steps == 2:
    _accum = 0.0  # 丢弃追不上的时间，避免死亡螺旋
```

### 2.3 客户端插值

客户端不跑物理，只做“延迟一帧的插值”：

- 维护最近 2~4 个快照，按 `server_tick * 0.05` 建立时间轴。
- 渲染时刻 = 本地估算的服务端时间 − **100ms**（约 2 个 tick 的缓冲）。
- 在相邻两个快照之间对位置/速度/yaw/能量做线性插值；yaw 用最短弧插值。
- 快照丢失时最多外推 100ms，之后冻结，等待下一帧，不产生“瞬移”。
- 客户端时钟用 `PONG` 的 `client_time_ms` 做偏移估计：`offset ≈ client_time - (server_time - rtt/2)`，再做滑动平均。

> 100ms 缓冲意味着玩家看到的世界比服务端晚约 100ms；这是服务端权威 + 无预测的必然代价。M6 先保证正确性，后续再评估客户端预测。

### 2.4 代码上报与执行

1. 玩家在客户端编辑器里写代码，本地只做**长度检查 + 语法检查**（用于即时提示，不作为安全边界）。
2. 点击“部署”后发送 `CODE`：`unit_uid + revision + source`。
3. 服务端重新校验长度/UTF-8/语法，编译成自有字节码，替换该单位的 VM。
4. 编译或运行失败：`ERROR` 回给客户端，单位保留旧代码或回退到默认悬停代码，**服务端不中断**。
5. 代码只在服务端执行；客户端永远拿不到“执行结果”以外的权威状态。

## 3. 传输层

### 3.1 为什么用裸 UDP + 自定义帧

M6.0 用 Godot 的 `PacketPeerUDP`，不用 `ENetMultiplayerPeer`，也不依赖 SceneTree 的 `multiplayer` API：

- 纯轮询接口，headless 下可创建、可测试；
- 快照可丢（下一帧会覆盖），输入可丢（下一 tick 有新输入），不需要 ENet 的可靠通道；
- 自定义 6 字节帧头最直观，方便后面做分片、加密、协议升级；
- 将来如果确实需要可靠通道/拥塞控制，可以在 `net_session.gd` 内部替换成 ENet，而不影响上层消息语义。

### 3.2 帧格式（小端）

| 偏移 | 类型 | 含义 |
|---|---|---|
| 0 | u8 | 协议版本 `PROTOCOL_VERSION = 1` |
| 1 | u8 | 消息 id `MSG_*` |
| 2..5 | u32 | 负载长度（字节） |
| 6.. | bytes | 负载 |

- 帧头固定 **6 字节**；版本不符、长度不符、未知 id 一律丢弃。
- 单帧负载上限 **1 MiB**（防御性上限）；实际最大的 `CODE` 为 64 KiB、`SNAPSHOT` 为 11.8 KiB。
- 当前所有快照都是**整帧**发送；2 队 × 20 单位时 933B，远小于常见 1200B MTU。
- 大战场（>50 单位）会超过 MTU，需要分片或 ENet；见 §8 限制。

### 3.3 会话模型

`net_session.gd` 自己持有 `PacketPeerUDP`：

- 服务端：`host(port)` 绑定端口；用 `get_packet_ip()/get_packet_port()` 识别远端，首次见到时分配递增 `session_id`，维护 `session_id ↔ ip:port` 映射。
- 客户端：`join(address, port)` 先绑定临时端口，再 `connect_to_host`；`session_id` 固定为 `SERVER_SESSION_ID = 1`。
- `poll()` 返回本帧所有消息，并把坏帧静默丢弃、计入 `dropped`。
- `send_to(session_id, ...)` 服务端按映射设置目标地址；客户端忽略 session_id 直接发给服务端。
- `broadcast(...)` 服务端遍历所有已知会话；客户端等价于发给服务端。

## 4. 消息类型表

方向：C→S = 客户端到服务端，S→C = 服务端到客户端，双向 = 两边都可能发。
“帧大小”= 6 字节帧头 + 负载；字符串按 UTF-8。

| id | 名称 | 方向 | 负载字段 | 频率 | 典型/最大帧大小 |
|---:|---|---|---|---|---|
| 1 | `HELLO` | C→S | `u8 team` + `u8 name_len` + 玩家名（≤64B） | 连接时 1 次；未收到 WELCOME 时每 500ms 重发 | 约 20B / 72B |
| 2 | `WELCOME` | S→C | `u32 session_id` + `u8 team` + `u8 tick_rate` + `u32 server_tick` + `u32 map_seed` | 连接时 1 次 | 20B |
| 3 | `CODE` | C→S | `u32 unit_uid` + `u32 revision` + `u32 source_len` + 源码（≤64KiB） | 部署/修改代码时；重连补发；限 5 次/分钟 | 约 200B~2KB；最大 65,554B |
| 4 | `SNAPSHOT` | S→C | 完整 `snapshot.gd` 字节流：`u8 ver + u32 tick + u16 count + count×23B` | 20Hz | 2 单位 59B；20 单位 473B；40 单位 **933B**；100 单位 2,313B |
| 5 | `INPUT` | C→S | `u32 tick` + `u32 unit_uid` + `u8 flags(bit0=drill)` + 5×`i8` 控制量（×100） | 手动接管时 ≤20Hz；代码单位默认不发 | 20B |
| 6 | `PING` | 双向 | `u32 nonce` + `u64 client_time_ms` | 1Hz | 18B |
| 7 | `PONG` | 双向 | `u32 nonce` + `u64 client_time_ms` + `u32 server_tick` | 收到 PING 即回 | 22B |
| 8 | `ERROR` | S→C | `u16 code` + `u16 msg_len` + 文本（≤512B） | 事件触发 | 10B~522B |

### 4.1 各消息细节

- **HELLO**：`team` 0=观战、1=蓝、2=红；`name_len` 为 u8。服务端校验名字长度和 UTF-8，重复 HELLO 视为重连请求。
- **WELCOME**：`tick_rate` 目前固定 20；`server_tick` 提供时间基准；`map_seed` 让客户端校验地图一致。
- **CODE**：`revision` 单调递增，服务端用它做幂等（同一 revision 重复收到只应用一次）。源码超过 64KiB 时编码端按字符截断，服务端仍会再校验。
- **SNAPSHOT**：负载就是快照本身，不再额外套 tick，避免每帧浪费 4B；字段见 §5。
- **INPUT**：控制量范围 −1..1，线上 `i8` 为 −100..100；越界在编码端夹紧、解码端再次夹紧。这是给“手动接管/调试/未来建造指令”用的通道，代码单位不需要。
- **PING/PONG**：`client_time_ms` 用发送方的单调时钟，服务端原样回传，客户端算 RTT；`server_tick` 用于估计服务端时间。
- **ERROR**：`code` 见下：

| 常量 | 值 | 含义 |
|---|---:|---|
| `ERR_BAD_PROTOCOL` | 1 | 版本/帧格式错误 |
| `ERR_CODE_REJECTED` | 2 | 代码语法/长度校验失败 |
| `ERR_NOT_AUTHORIZED` | 3 | 未加入房间或无权操作该单位 |
| `ERR_ROOM_FULL` | 4 | 房间已满 |
| `ERR_RATE_LIMITED` | 5 | 消息频率超限 |
| `ERR_SERVER_BUSY` | 6 | 服务端内部错误 |

## 5. 快照格式与量化

### 5.1 布局

```
u8   version = 1
u32  tick
u16  unit_count (<= 512)
repeat unit_count:
  u32 uid
  u8  team
  i16 pos.x, pos.y, pos.z   (厘米)
  i16 vel.x, vel.y, vel.z   (厘米/秒)
  i16 yaw                   (弧度 × 10000)
  i32 energy                (焦耳)
```

- 头部 **7 字节**，每单位 **23 字节**，单帧最大 `7 + 512×23 = 11,783` 字节。
- 定长记录的好处：解析不需要循环里的变长分支；单位数少时可以按索引直接寻址。

### 5.2 量化与精度

| 字段 | 线上类型 | 比例 | 范围 | 最大量化误差 |
|---|---|---|---:|---:|
| 位置 | i16 ×3 | 100 / 米（厘米） | ±327.67 米 | 0.005 米 |
| 速度 | i16 ×3 | 100 / (米/秒) | ±327.67 米/秒 | 0.005 米/秒 |
| yaw | i16 | 10000 / 弧度 | ±3.2767 弧度 | 0.00005 弧度 |
| 能量 | i32 | 1 / 焦耳 | ±2.147e9 焦耳 | 0.5 焦耳 |

- 地图 256×256，位置用厘米 i16 有 ±327 米余量；如果未来地图扩大，需要改成 i32 或按区块相对坐标。
- yaw 编码前 `wrapf(yaw, -PI, PI)`；跨 ±π 时客户端用最短弧插值，避免转一圈。
- `NAN/INF` 一律写 0，防止服务端物理异常污染整包；`parse()` 对空数组、截断、版本不符、`count > 512`、长度不符都返回 `ok=false`，不越界读取。
- `capture()` 超过 512 个单位时只保留前 512 个；这是保护上限，不是正常玩法上限。

### 5.3 与协议层的关系

`MSG_SNAPSHOT` 的 payload 就是上述字节流；`protocol.encode_snapshot()` 只做大小校验和复制，`protocol.decode_snapshot()` 调用 `snapshot.parse()`。这样：
- 传输层不需要理解单位语义；
- 快照格式可以单独测试、单独演进版本号。

## 6. 连接、断线与重连

### 6.1 建立连接

```
客户端                                  服务端
  | -- HELLO(team, name) ---------------> |
  | <------------- WELCOME(session, tick) |
  | -- CODE(unit, rev, source) ---------> |
  | <------------- SNAPSHOT(20Hz) -------- |
  | -- PING(1Hz) -----------------------> |
  | <------------- PONG ------------------ |
```

- 客户端在收到 `WELCOME` 前每 500ms 重发一次 `HELLO`（UDP 可能丢包）。
- 服务端对同一 `ip:port` 的重复 `HELLO` 只回 `WELCOME`，不重复创建玩家。
- 客户端收到 `WELCOME` 后：清空插值缓冲、记录 `server_tick`、把本地缓存的所有单位代码用 `CODE` 重发。

### 6.2 心跳与超时

- 双方 1Hz 发 `PING`；收到即回 `PONG`。
- 服务端超过 **5 秒**没有收到某会话任何包 → 标记 `stale`，暂停接收其输入。
- 超过 **30 秒** → 移除会话，单位转为“无人控制”（默认悬停）或按规则销毁。
- 客户端超过 **5 秒**没有收到快照 → 显示“重连中”，冻结画面，不本地模拟。

### 6.3 重连

M6.0 的 UDP 会话没有 token/加密，重连按“新会话”处理：

1. 客户端保留：最后一份代码缓存、玩家名、队伍、最后 tick。
2. 重新 `join` → 新 `HELLO` → 服务端分配新的 `session_id`（如果旧会话还在宽限期，按玩家名/令牌接管；M6.1 加 token 后改为严格接管）。
3. 服务端在宽限期（建议 60 秒）内保留单位与代码；重连后立即发全量快照，客户端重建插值缓冲。
4. 客户端 `CODE` 的 `revision` 继续递增，服务端以 revision 幂等去重。
5. 若重连失败或版本不一致：显示错误，不进入游戏。

> 已知缺口：当前 `HELLO` 只有名字和队伍，没有身份令牌，理论上可被同网段伪造。M6.1 在 `WELCOME` 里下发随机 `session_token`，后续消息带上 token；正式上公网前必须加。

### 6.4 消息可靠性策略

UDP 本身不保证送达，按消息价值分级：

| 消息 | 丢包策略 |
|---|---|
| `SNAPSHOT` | 可丢；下一帧覆盖，客户端插值/外推兜底 |
| `INPUT` | 可丢；下一 tick 有新输入；关键操作（部署/建造）改走带重发的命令 |
| `PING/PONG` | 可丢；连续 5 秒没有有效心跳才判超时 |
| `HELLO` | 500ms 重发，直到收到 `WELCOME` |
| `CODE` | 客户端每 500ms 重发同一 revision，最多 5 次；服务端 revision 幂等 |
| `ERROR` | 可丢；客户端可用“拉取状态”或下一次操作的结果兜底 |

M6.0 的 `net_session.gd` **不实现重传队列**，只提供收发；上表的重发逻辑放在上层会话管理器（Lead 集成时实现）。

## 7. 作弊与 RCE 防护

### 7.1 信任边界

- **客户端零权威**：客户端的坐标、tick、伤害、资源数字都不被信任；服务端只接受 `HELLO/CODE/INPUT/PING` 四类意图。
- **代码只在服务端执行**：客户端上传的是源码字符串，不是字节码、不是可执行文件、不是“执行结果”。客户端本地只做编辑器提示用的语法检查。
- **服务端不把代码发回给其他客户端**：避免源码泄露（如果未来要做观战/回放，单独脱敏）。

### 7.2 沙箱 VM（已有能力）

项目现有 `scripts/lang/py_vm.gd` 是纯 GDScript 字节码 VM：

- 不调用 Python 解释器、不开子进程、不碰文件系统/网络；
- 只暴露白名单内建函数（`print`、`set_lift`、`set_tilt`、`set_rcs`、`drill`、`range/len/...`）；
- 有单行内存保护、循环重复上限、每 tick 指令预算；
- 错误只写 `vm.error`，不会把服务端打崩。

M6 在此之上再加：

- 源码长度 ≤ 64KiB（协议层 + 服务端双重检查）；
- 每单位每 tick 指令预算（例如 20,000 条指令），超预算暂停到下一 tick；
- 每玩家代码上传频率限制（例如 5 次/分钟），超限回 `ERR_RATE_LIMITED`；
- 编译失败回退到默认悬停代码，单位不消失、服务端不崩。

### 7.3 网络输入校验

服务端对每条消息都做：

1. 帧层：版本、id、长度、`payload` 上限（`protocol.decode_message`）。
2. 消息层：字段长度、字符串 UTF-8、`count <= 512`、控制量夹紧（`decode_*`）。
3. 会话层：该 `session_id` 是否已 `WELCOME`、限速（INPUT ≤ 30/s、PING ≤ 2/s、CODE ≤ 5/min）。
4. 业务层：`unit_uid` 是否属于该玩家/队伍、revision 是否单调、操作距离/资源是否合法。
5. 数值层：所有浮点写入物理前 `is_finite` 检查；位置/速度夹紧。

任何一层失败：丢弃 + 可选回 `ERROR`，不计入游戏状态。

### 7.4 RCE / DoS 清单

| 风险 | 防护 |
|---|---|
| 玩家代码执行系统命令 | VM 无 `os`/`subprocess`/`FileAccess`/`HTTPRequest` 等入口，只有白名单内建 |
| 恶意超长源码撑爆内存 | 客户端与服务端都限制 64KiB；协议帧负载上限 1MiB；VM 源码行长度限制 |
| 构造超长字符串/大列表 | VM 的 MemoryError 保护 + 指令预算 |
| 伪造超大 `unit_count` / 长度字段 | `decode_message` 与 `snapshot.parse` 先校验再读 |
| 高频包打满 CPU | 每会话限速 + 每帧处理包数上限 + 丢弃坏帧 |
| 伪造他人 `session_id` | M6.1 加 session token；M6.0 只适合局域网/好友测试 |
| UDP 反射/放大 | 不回显大包；`PING` 回包固定 22B；上线前加 token 校验 |
| 客户端改内存/改快照 | 客户端显示层不参与判定；服务端快照是唯一事实 |

> 结论：**RCE 的主要风险不在“玩家代码”，而在“网络解析”**。因此本层把“所有长度先校验、所有数组有上限、所有循环有边界”作为硬规则。

## 8. 带宽估算

### 8.1 公式

```
快照帧大小  B_snap = 6 (帧头) + 7 (快照头) + 23 × N
单客户端下行 = 20 × (B_snap + 28)   B/s     # 28 = IPv4 头 20 + UDP 头 8
服务端总下行 = 客户端数 × 单客户端下行
单客户端上行 ≈ 20 × (20 + 28) + 1 × (18 + 28)  B/s   # INPUT + PING
```

### 8.2 典型规模（2 队，每队 20 单位，共 40 单位）

- 快照负载：`7 + 40×23 = 927B`
- 快照帧：`6 + 927 = 933B`
- 加 IP/UDP：`933 + 28 = 961B`
- 20Hz 下行：`961 × 20 = 19,220 B/s ≈ 18.8 KiB/s ≈ 153.8 kbit/s`
- 两个客户端时服务端总下行：`≈ 38.4 KB/s ≈ 307.5 kbit/s`
- 单客户端上行（INPUT 20Hz + PING 1Hz）：`≈ 960 + 46 = 1,006 B/s ≈ 8.0 kbit/s`
- 1v1 总带宽（粗算）：`307.5 + 2×8.0 ≈ 323.5 kbit/s`

### 8.3 不同单位数的单客户端下行

| 单位数 N | 快照帧 | 20Hz 帧流量 | 加 IP/UDP 后 | 说明 |
|---:|---:|---:|---:|---|
| 2 | 59B | 1.18 KB/s ≈ 9.4 kbit/s | ≈ 13.9 kbit/s | 1v1 各 1 单位 |
| 20 | 473B | 9.46 KB/s ≈ 75.7 kbit/s | ≈ 80.2 kbit/s | 10v10 |
| 40 | 933B | 18.66 KB/s ≈ 149.3 kbit/s | ≈ 153.8 kbit/s | **M6 目标规模 20v20** |
| 100 | 2,313B | 46.26 KB/s ≈ 370.1 kbit/s | ≈ 374.6 kbit/s | 50v50，已超过单包 MTU 建议值 |
| 512 | 11,789B | 235.8 KB/s ≈ 1.89 Mbit/s | ≈ 1.89 Mbit/s | 快照上限，必须分片 |

### 8.4 结论

- M6 目标规模（2×20）下单客户端下行约 **150 kbit/s**，服务端 2 人约 **0.3 Mbit/s**，普通宽带/热点都能承受。
- 上行只有个位数 kbit/s，因为单位控制由服务端代码产生，客户端不需要每帧上传摇杆数据。
- 快照占绝对大头；后续优化优先级：**兴趣管理（只发视野内单位）> 增量快照 > 降低快照频率 > 位压缩**。
- 当前 `SNAPSHOT` 每帧全量、无 delta；40 单位以内不需要优化。

### 9.4 集成顺序（Lead）

1. 在 `main.gd` 里持有一个 `NetSession`；服务端每 tick 调 `poll()` 处理 HELLO/CODE/INPUT，然后 `broadcast(SNAPSHOT)`。
2. 客户端每帧 `poll()`，把快照塞进插值缓冲；收到 `WELCOME` 后启动 1Hz `PING`。
3. 单位管理器提供 `capture` 需要的 `[{uid, team, pos, vel, yaw, energy}]`；`snapshot.capture()` 不依赖任何场景节点。
4. 代码上传由 UI 触发，服务端用现有 `py_vm` 编译/运行；`protocol.decode_code()` 的结果直接喂给 VM。
5. 所有网络错误只影响 UI 提示，不 `push_error` 到主循环导致崩溃。

## 11. 已知限制与后续

1. **无加密/认证**：M6.0 只适合本机/局域网/好友测试；公网前必须加 session token，最好用 DTLS 或 Steam Datagram Relay。
2. **无可靠通道**：`CODE` 依赖上层重发；`net_session.gd` 只做数据报收发。
3. **无分片**：>50 单位的快照会超过 1200B MTU，需要分片或换 ENet；当前 512 单位上限只是解析保护。
4. **无兴趣管理**：所有客户端收全量快照；人多了以后按视野/队伍裁剪。
5. **无客户端预测**：高延迟玩家会感觉操作延迟约 RTT + 100ms；后续评估预测/回滚。
6. **`get_local_port()` 返回请求端口**：服务端 `host(0)` 时无法得知实际端口（当前只支持显式端口）。
7. **IPv6/NAT**：未做地址族协商和打洞；M6.0 默认 IPv4。
8. **环境差异**：headless 下 UDP loopback 在本机已通过；如果某些 CI/沙箱拦截 UDP，测试会记为“跳过”并保留原因，而不是失败。
